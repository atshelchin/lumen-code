## 1 现状评估（2026-10-20）

### 1.1 协议要解决什么问题

Lumen Code 把文件从一块屏幕传到一台相机：发送端播放一串彩色格子帧，接收端拍摄、解码、重建文件。没有网络、没有配对、没有回传信道，接收端随时加入、随意丢帧。

核心设计理念：

- **单向广播 + 喷泉码**：每个包都是新信息，接收端不需要特定帧，也不需要回传。
- **分层纠错**：帧头 4 份副本 + CRC-16；每个码字 RS(n, k)；每个包 CRC-16；整个文件 CRC-32 + 长度。
- **适配相机**：彩色格子（C4 默认，2 bit/格）、网格自适应屏幕、3/4 角定位、对齐标记点阵、Hilbert 顺序让一帧撕裂只损失少量码字。
- **零依赖**：JS 与 Rust 两个参考实现都不依赖第三方库（Rust 自带 DEFLATE）。

目标运行环境和技术栈：

| 环境 | 代码 | 技术 |
|---|---|---|
| 浏览器（静态站点） | `src/core`、`src/web`、`dist/` | ES modules，Web Worker，WebAssembly |
| Rust 原生 / WASM / C ABI | `src/rust` | Rust 2021，零依赖 |
| 原生 App 共享核心 | `src/app` | Rust + Crux + uniffi |
| iOS / Android / 桌面 | `src/ios`、`src/android`、`src/desktop` | SwiftUI / Compose / GPUI |

### 1.2 完成度

**已完成且可靠**（有测试、两实现一致）：

- 帧格式：网格、finder、角标、分隔线、对齐点阵、Hilbert 数据顺序、白化、4 份帧头与掩码、调色板。
- 码字层：RS 编解码（含擦除）、码字到格子的映射、填充。
- 包格式与描述符的**编码**；喷泉码编码/解码；分块计划。
- 测试向量（发送侧）：JS 生成，Rust 逐项复现；JS 与 WASM 发送端帧逐位一致；JS→WASM 互通。
- 扫描器（JS 与 Rust 两份）：相机模拟器、鲁棒性批测，真机已跑通（见 README 和记忆中的实测数据）。
- 原生 App 与 Web demo 已在真机上传输成功（iPhone 11、Redmi K40）。

**只做了一半**：

- **接收端的规则**：规范只写了“推荐”，没有规定接收端在每种状态下收到每种包时怎么办。实现里有空白（见 1.3）。
- **输入校验**：帧头、包、描述符的合法性检查不完整；描述符的 TLV 和保留标志位只在规范里出现，实现完全没解析。
- **测试向量只覆盖发送侧**：没有“这个输入必须被拒绝”的反例向量，没有喷泉解码向量，没有包流→文件的端到端向量。JS 端没有测试去**校验**向量文件（它只负责生成），改了 JS 行为再重生成，回归就悄悄过去了。
- **测试**：Rust 协议 crate 只有 7 个测试；没有模糊/属性测试；没有恶意输入测试。

**还没做**：

- 规范中的安全考虑、资源上限、错误处理、状态机、时序（seq 回绕）章节。
- 性能结论缺少统一的测量方法说明；喷泉码“约 K+2 个符号即可解码”的说法没有测量依据。

### 1.3 规范与实现不一致之处（以及以哪边为准）

1–8 已用脚本对当前实现实测确认，不是推测（这些场景随后都变成回归测试，见 P4）：

| # | 问题 | 规范 | 实现 | 结论 |
|---|---|---|---|---|
| 1 | 一个 RS 误纠且恰好通过 CRC-16 的错包（或 TID 碰撞的外来包）进入喷泉解码器 | 只说“交付前检查长度和 CRC-32” | 检查失败后**永久卡死**：每次都报 checksum error，再多的包也救不回来（JS、Rust 同） | 两边都不对。规范要规定：校验失败则丢弃该传输全部状态（含描述符）重新收集 |
| 2 | 解压炸弹 | 未提 | JS 用 `DecompressionStream` 不设上限：65 KB 负载解出 64 MB（声明文件大小 10 字节）。Rust 有上限 | 以 Rust 为准，写进规范：解压输出 MUST 以描述符中的文件大小为界 |
| 3 | 帧头合法性 | 只查 `n ≥ 24, 2 ≤ nsym < n` | 同规范，于是 `n=24, nsym=22`（T = −5）被接受 | 规范不完整。补上 `T ≥ 16`（即 `n − nsym ≥ 23`）和 `m ≥ 1` |
| 4 | 描述符保留标志位 | “其他位为 0” | 接收端忽略，置位也照样交付 | 规范要定义语义：标志位是“关键扩展”，未知位置位 MUST 拒绝；TLV 是“非关键扩展”，未知类型忽略 |
| 5 | 描述符资源上限 | 未提 | 512 MB 的描述符被接受，立即分配 128 个解码器（RSS +77 MB），之后可涨到 512 MB | 规范要求接收端设上限并拒绝超限传输 |
| 6 | 描述符名字长度 `N > T − 15` | 发送端 MUST NOT | 接收端悄悄截断 | 改为接收端 MUST 拒绝（严格解析） |
| 7 | 元数据包 `SBN ≠ 0` | 发送端 MUST 置 0 | 接收端忽略 SBN 照收 | 接收端 MUST 忽略这种包 |
| 8 | 包长度 | `T ≥ 16` | Rust 只查 `len ≥ 8`，JS 不查 | 统一为 `T ≥ 16` |
| 9 | 同一 (TID, T) 出现内容不同的描述符 | 未提 | 保留第一个，后续包混进同一个解码器 | 规定：视为新传输，丢弃旧状态 |
| 10 | 跳帧键 `(seq, X, Y, mode, n, nsym)` 的有效期 | 未提 | Web 与 App 都用 4000 ms；seq 是 8 位，60 fps 下 4267 ms 回绕，余量只有 6 %，高于 64 fps 会错跳新帧 | 规范规定上限（1 s，对 ≤ 255 fps 都安全），实现跟随 |
| 11 | §13 一致性要求 | 要求发送端与向量“逐位一致”，输入包括 ECC 等级 | 但 §10.2 说包调度只是推荐，§10.4 说 n/nsym 选择是参考性的 | 规范自相矛盾。改为：帧编码（给定包和参数）必须逐位一致；调度和参数选择是策略，不属于一致性 |
| 12 | “约 K+2 个符号可解码” | 参考性说法 | 现有测试显示平均超额 0.9–2.0，最大 10 | 需要测量并给出失败概率表 |
| 13 | 描述符总在码字 0 | §10.2 推荐“放在第一个” | 码字 0 是 Hilbert 曲线起点，即左上角。实测：左上角被眩光遮住时（README 宣称的“一角被遮仍可解码”场景），120 帧收到 1104 个数据包（K 的 7 倍）、0 个描述符，**传输永远完成不了** | 参考发送策略的缺陷，不是线格式问题。改为描述符位置在帧内轮换（伪随机），接收端本来就接受任意位置 |

### 1.4 是否已发布、兼容成本

- GitHub 仓库公开（0 star，0 fork）。桌面 App v0.1.0 / v0.1.1 以 pre-release 形式发布，资产下载总数个位数（多半是作者本人）。规范状态写的是 “Draft for public review”。
- 结论：**线格式已经被一个公开发布的程序实现**，所以改线格式需要你的同意（按你的要求，这属于要停下来问的情况）。但兼容成本很低。

**本轮评估的结论是：不需要改线格式。** 上面所有问题都能在不改变任何已发送比特的前提下解决：要么是收紧接收端的校验（参考发送端从未产生过这些非法值），要么是规定接收端行为。v0.1.x 发送的帧，新接收端照收；新发送端的帧，v0.1.x 接收端也照收（只是旧接收端保留着那些缺陷）。

我考虑过、但决定**不做**的线格式改动（理由见第 3 节决策记录）：TID 扩到 32 位、喷泉码换成 RaptorQ、seq 扩位、给每个分块加 CRC。

## 3 决策记录

（每条：问题、选择、理由、代价。）

### D1 不改线格式

见 1.4。所有已知缺陷都在接收端规则和校验层面，改线格式只增加兼容成本，没有收益。

### D2 不把 TID 扩到 32 位

16 位 TID 的风险是两个传输碰撞（1/65536，且还要 T 相同）。碰撞的后果由 D3 处理：内容不同的描述符会触发重置，文件校验失败也会触发重置，所以碰撞最坏只是浪费一些已收集的包，不会交付错误文件，也不会卡死。扩位要每包多 2 字节（约 1 %）并破坏兼容。

### D3 文件校验失败 → 丢弃该传输全部状态

喷泉解码无法定位哪个符号是坏的（错误会通过消元扩散），文件级 CRC-32 也无法定位到分块。最简单且正确的恢复是丢弃该 (TID, T) 的全部状态（包括描述符，因为坏的可能就是描述符本身），重新收集。按 RS 误纠率和 CRC-16 估算，正常信道下这种事件极罕见，所以重新收集的代价可以接受；关键是不再卡死。

### D4 不换 RaptorQ

RaptorQ（RFC 6330）标准、系统码、超额更低，但实现复杂（GF(256) HDPC、系统索引表），两个零依赖实现各要上千行，而且破坏兼容。对单向相机信道来说，系统码也没有实际好处（总会丢帧，总要解码）。

测量结果（规范附录 C.2，`measure fountain/tail/rank`）支持保留：K ≤ 1000 时与 GF(2) 随机码的理论曲线一致（K 个符号失败 71 %，每多一个减半，平均多 1.6 个）；K 越大尾部越长，K = 16384 平均多 2.4 个，1000 次中最多多 47 个，约 1.5 帧。用独立的稠密 GF(2) 秩判定验证过：参考解码器失败的每个集合确实不满秩，所以尾部是码本身的性质，不是解码器的缺陷。代价是可忽略的额外帧和一两次重试解码（Rust 20 ms，JS 105 ms）。记为已知限制；如果将来出 v2，可像 RaptorQ 那样加 GF(256) 稠密行来压尾部。

**用户决定（2026-10-20）：保留现有喷泉码，不改。** 理由：已经有用户下载使用，改动会破坏兼容。今后线格式的兼容性是硬约束：任何会让已发布版本无法互通的改动都不做。

### D5 seq 保持 8 位，规定跳帧窗口 ≤ 1 s

跳帧只用于避免同一帧被重复解码，同一帧被重复拍到只发生在它显示的那一小段时间里。1 s 窗口对 ≤ 255 fps 的发送端都不会把新帧误认为旧帧。扩位会占用保留位、破坏兼容，没有必要。

### D6 严格解析

新协议没有历史包袱，接收端对非法输入一律拒绝，而不是“尽量猜”（参考 RFC 9413 对 Postel 定律的反思）。扩展只通过明确定义的位置进行：帧头 version、描述符 version、描述符标志位（关键：未知位置位则拒绝）、TLV 类型（非关键：未知类型忽略）、元数据索引（未知索引忽略）。

### D7 描述符位置轮换（参考发送策略，不改线格式）

问题：描述符总放在码字 0，即左上角；左上角被眩光遮住时传输永远完成不了（见 1.3 #13）。
选择：第 c 个描述符放在码字 `mix32(c) mod m`（规范 §10.2）。伪随机而不是 `c mod m`，因为相邻码字在空间上相邻（Hilbert 顺序），顺序轮换会连续几次落在同一块坏区域里。
代价：参考发送端的帧变了（`referenceSender` 向量重新生成）；不影响任何接收端，接收端本来就接受任意位置。实测：同样的眩光场景 120 帧收到 14 个描述符，传输完成。

### D8 JS 接收端用自己的严格 inflate

问题：JS 用平台的 `DecompressionStream`（zlib），没有输出上限；而且 zlib 与 Rust 自带 inflater 对畸形流（尾随字节、超额码表）判定不同，两个参考接收端会对同一个传输给出不同结果。
选择：把 Rust inflater 移植到 JS（`src/core/inflate.js`，约 170 行），两边按同一套严格规则修改：恰好一个流、最终块之后不得有字节、码表不得超额、HLIT/HDIST 上界、必须有块结束码、输出以 F 为界。规范 §9.1 写明。
代价：多 170 行代码；接收端不再依赖 `DecompressionStream`（发送端压缩仍用它，压缩率更好，压缩是发送端的自由）。性能 147 MB/s，够用。

### D9 接收端上限取值

最大 256 MiB（同时约束 L 和 F，否则小 L 大 F 的描述符能让解压分配 4 GB）、每个键最多保留 4096 个描述符到达前的包（约 1 MB，足够 100 帧以上）、最多 4 个键（淘汰最久未收到包的）。256 MiB 与 App 发送端原有的 `MAX_FILE` 一致。

### D10 测试向量结构改为第 2 版

原向量只覆盖发送侧，且 JS 端只生成不校验。新结构分编码、解码（每个非法用例恰好一个缺陷）、包流（状态机逐步的动作和结果）、差分语料摘要、参考发送端（参考性）。三处校验：JS、Rust、WASM 构建；`npm test` 在向量文件与代码不一致时失败。

### D11 差分测试

两个实现有相同的 `Rng`，所以能用同一种子生成同样的伪随机语料；比较判定结果的 CRC 摘要，就能用很少的向量数据比较成千上万个边界情况。这比单独的模糊测试更强：它发现的是两个实现之间的分歧，而不只是崩溃。

### D12 帧键有效期从“最后一次看到后 4 s”改为“首次记录后 1 s”

seq 只有 8 位，60 fps 下 4.27 s 回绕；4 s 窗口只差 6 %，且按“最后一次看到”计时，同一帧被反复看到会一直续期。1 s 对 ≤ 255 fps 都安全；统计用的条目保留时间不变。

### D13 文件名在进入应用的那一点统一清洗

问题：iOS/Android 只替换 `/`，桌面把原始名字直接给保存对话框，Web 依赖浏览器；控制字符和双向覆盖字符（可伪装扩展名，如 `invoice‮fdp.exe`）原样显示。
选择：一条规则（路径分隔符和文件系统拒绝的字符 → `_`，删除控制字符与双向覆盖字符，空名、`.`、`..` → `file`），Web 在 `text-view.js`，原生在 App 核心的接收线程（`format::safe_name`），这样三个原生外壳的显示、保存、分享、打开都自动拿到安全名字。规范 §13 写明要求。

### D14 修复 MSRV、加 CI

`Cargo.toml` 声明 `rust-version = 1.73`，但 main 上就编译不过（scan.rs 依赖 1.79 的临时值生命周期延长）；改为局部变量，1.73 实测通过。新增 `.github/workflows/test.yml`：JS 与 Rust 全部测试、MSRV 构建、App 核心测试、headless Chrome 端到端。工作流本身要推送后才会在 GitHub 上运行；我在全新克隆里按相同步骤跑通了（macOS）。

### 4.2 关键设计决策（详见第 3 节 D1–D14）

- **不改线格式**（D1）：所有缺陷都在接收端规则和校验层；新旧实现双向互通。
- **改动的已有设计**：参考发送端的描述符位置（固定 → 伪随机轮换，D7，修复左上角被遮时永不完成）；JS 接收端解压（平台 zlib → 自带严格 inflate，D8）；帧键窗口（最后看到后 4 s → 首次记录后 1 s，D12）；一致性条款（发送端逐位一致 → 编码器逐位一致、调度自由）；描述符标志位语义（“其他位为 0” → 关键位，置位即拒绝）；空文件名（JS 编码器不再替换成 `file`）。
- **评估后保留的已有设计**：16 位 TID（D2）、自定义喷泉码而非 RaptorQ（D4，有实测与秩判定支撑）、8 位 seq（D5）、帧头格式。
- **校验失败的恢复方式**（D3）：整个传输重来，而不是试图定位坏包。

### 4.4 未解决的限制与风险

1. **本轮没有做真正经过镜头的跨设备实测。** 三个原生 App 都是“自己的帧渲染后喂给自己的扫描器”，Web 用的是相机模拟器生成的视频。本轮改动不涉及光学层（只有描述符换了位置），以前会话的真机结果（Android → iPhone 96 KB/s）应仍然成立，但需要你手持设备确认一次。
2. **喷泉码大块尾部较长**：K = 16384 时 2 % 的块需要多于 16 个额外符号，最多观察到 47 个（约 1.5 帧）。实际影响很小；要消除需改线格式（v2）。
3. **没有机密性和认证**：按设计如此，规范 §13 写明。
4. **CI 工作流尚未在 GitHub 上运行过**（需要推送）；Windows/Linux 桌面版本轮没有重新构建（改动的 App 核心与平台无关）。
5. **Safari 没有自动化测试**；接收端不再依赖 `DecompressionStream`，旧版 Safari 兼容性反而更好。
6. **已发布的 v0.1.x 桌面版**仍有旧缺陷（错包后卡死等），与新版互通没有问题。

### 4.5 需要你决定的事

1. **是否推送分支、合并到 main**（对外操作，我没有做）。
2. **是否发布桌面 v0.1.2**，以及 Web 演示站是否重新部署（我不知道它部署在哪里）。
3. **是否冻结 v1**：喷泉码已决定保留（见 D4），线格式实际上已经定型；建议在你做完一次真机光学互通确认后，把第 2 稿正式冻结为 v1。
4. **真机光学测试**：需要你手持手机对准屏幕（Web 发送 → 手机 App 接收、手机 ↔ 手机），各一次即可。
