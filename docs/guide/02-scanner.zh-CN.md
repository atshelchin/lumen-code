# 2 · 接收端如何读出一帧

[指南目录](README.zh-CN.md) · [English](02-scanner.md) · 规范对应章节：§11（§11.6 为资料性） · 代码：`src/core/scan.js`、`src/rust/src/scan.rs`

规范只规定帧是什么样，不规定怎么读。本篇讲参考识别器怎么做、为什么这样做。JS 和 Rust 两个识别器算法一致，Rust 版编译成 WebAssembly 快约 1.5–2 倍，原生代码快 1.6–2.8 倍。

## 2.1 现实中的照片有多糟

发送端画的是完美的网格，但相机拍出来的照片有下面这些问题：

| 现象 | 来源 | 对识别的影响 |
|---|---|---|
| 透视、旋转 | 手没拿正 | 网格不再是矩形 |
| 桶形 / 枕形畸变 | 手机广角镜头 | 连直线都是弯的，只靠四个角算不准中间 |
| 模糊 | 对焦不准、手抖、运动 | 黑环变细、格子颜色互相渗透 |
| 光晕（bloom） | 屏幕亮、曝光高 | 亮的部分"胖"一圈 |
| 摩尔纹 | 屏幕像素与相机像素的拍频 | 一片区域整体偏亮或偏色 |
| 颜色串扰、白平衡 | 相机色彩处理、屏幕色域 | 青可能偏绿，黄可能偏白 |
| 撕裂帧 | 卷帘快门 + 屏幕换帧 | 上下两半来自不同的帧 |
| 4:2:0 色度下采样 | 视频编码 | 颜色分辨率只有亮度的一半 |
| 反光、遮挡 | 环境光、手指 | 一个角或一块区域完全看不见 |

参考识别器的每个步骤对付其中一两项。测试用的相机模拟器（`test/camera.js`）把这些现象全部叠加在一起。

## 2.2 十个步骤

### ① 预处理（亮度与局部阈值）

把 RGB 转成亮度。按 16×16 像素分块（大图 32×32），记录每块的最小、最大亮度；每个像素的阈值取周围 5×5 块范围的**中点**。

- 为什么用最小/最大的中点，不用平均值？靠近码的边缘时，一个块里大部分是黑色静区，平均值会偏向墨色，把白环判成黑的。
- 平坦区域（背景、传感器噪声）的局部范围要达到全图范围的 30%（且不低于 40 级）才二值化，否则一张噪声大的照片会冒出上千个"定位图案"。

### ② 找定位图案

逐行扫描二值图像，寻找"纸-墨-纸-墨-纸 = 1:1:3:1:1"的游程，再在竖直方向交叉检验。角标同理，比例 1:2:1:2:1。

- 容差故意放宽，因为模糊会让黑环变细，光晕会让亮部变胖。多找到几个假的没关系，后面的步骤（模块拟合、帧头 CRC、校准点验证）会把它们淘汰。
- 每个模块至少 2 个像素，所以扫描时隔一个像素取样，速度翻倍。

### ③ 选三个角

四个角（三个定位图案 + 角标）中**任意三个**就够了：三个定位图案，或两个定位图案加角标。候选按"像不像一个网格的三个角"（距离比例、夹角、大小一致性）排序后逐个尝试，镜像方向也试（从镜子里或背面拍屏幕时）。所以一个角被反光挡住也能解码。

### ④ 测量格子大小

在每个定位图案处，沿两条轴找出六个环边缘的位置。边缘取在亮度**梯度的极值点**，不取阈值交点，因为模糊会让阈值交点系统性偏移。然后拟合 `t = c0 + m·k + δ·e`：m 是模块大小，δ 吸收"黑环变细 / 亮部变胖"这类对称的偏差。

### ⑤ 读帧头

帧头副本就在定位图案旁边，用刚测出的模块大小和方向采样它的 70 个格子。

- 模块大小总有误差，所以尝试 17 个缩放假设（±10%）；
- 每个假设用两均值迭代求一个阈值，它和全局阈值各试一次；
- CRC 正确就成功；
- 每个副本都失败时，把各副本"最清晰的那个假设"的软值（−1 到 +1）去掉掩码后相加，做**软多数表决**。与其余副本超过 1/4 的位不一致的副本，视为读错了位置，排除在外。这能处理常见的情况：每个副本都错一两位、但错的位置不同，相加后就对了。
- 仍然读不出时，**沿用上一个读对的帧头**：同一次传输中网格尺寸、颜色模式、码字长度、纠错字节数都不变，而解数据不需要帧序号。这一步只在所有角组合（含镜像）都试过之后才做；用错了会被尺寸检查、校准点验证和数据包 CRC 拦下，连续 3 次无收获就丢弃缓存。在"手持、没对准"的测试中，它让 C4 的解出帧数从 81/100 提高到 88/100，没有任何错误数据通过。这样解出的帧没有帧序号，不参与跳帧和帧率统计。

### ⑥ 建立网格几何

这一步决定了能不能读准成千上万个格子。

1. 从三个角出发，**逐步**寻找校准点：每个点的位置由已找到的邻居做加权局部仿射预测，再在小范围内搜索"中心亮、八邻域全暗"的图案。这样就能一点点跟上透视和畸变。
2. 对所有已找到的点做最小二乘单应性拟合（加上沿已知边的虚拟点作为约束），再用邻近点的**残差**做平滑插值，修正镜头畸变。
3. **校准点验证**：如果某组角预测的点阵位置几乎找不到校准点（少于 60%），说明其中一个"角"是假的（比如数据区里碰巧长得像定位图案的一块），放弃这组角，试下一组。
4. 每四个相邻校准点围成一个小四边形，各有一个单应性矩阵，每个格子用所在小四边形的矩阵定位。

### ⑦ 采样颜色

每个数据格子取中心点（权重 2）和上下左右偏移 0.18 格的四个点求平均。只采样**还没解出**的码字所在的格子，同一帧再次拍到时，已解出的码字不再重复计算。

颜色用局部参考归一化：每个校准点的中心是纸色、周围是墨色，所以每个小四边形都有自己的白和黑。格子颜色按位置在四个角的参考之间插值、映射到 0–1，这样就消除了暗角、亮度不均和大部分白平衡偏差。

### ⑧ 分类

以名义调色板为初值做 k-means 聚类，得到每个格子的颜色索引和**置信度**（到最近和次近聚类中心的距离差）。

然后做一次**局部增益校正**：按 4×4 格分块，用每块中格子的分类结果估计该块每个通道的增益（稀疏的块被拉向 1），双线性插值后重新分类。摩尔纹和局部偏色主要靠这一步对付。

### ⑨ Reed–Solomon 译码

格子比特拼回字节，逐个码字做 RS 译码：

1. 先直接译码（最多纠正 nsym/2 个错误字节）；
2. 失败时，把**置信度最低**的字节标为擦除后重试，先标 nsym/4 个，再标 nsym/2 个。一个擦除只消耗一个错误一半的纠错能力，所以能纠更多错；
3. 擦除最多 nsym/2 个，始终保留至少 nsym/2 字节冗余。擦除太多时 RS 会把随机数据"纠正"成某个合法码字；
4. 最后用数据包的 CRC-16 再过滤一道。

### ⑩ 去重与跳帧

接收端用（seq, X, Y, mode, n, nsym）标识一帧。相机通常每秒 30 帧，而发送端每秒只换 10–12 帧，所以同一帧会被拍到好几次：

- 如果这一帧的所有码字都已解出，下次只读帧头就返回（JS 约 8 ms，而完整解码 14–45 ms）；
- 如果只解出一部分，下次只采样剩下的码字。

seq 只有 8 位，所以同一个键每 256 帧就会重复一次（60 FPS 下为 4.3 秒）。因此一个键只在这一帧首次解出后的 1 秒内代表这一帧（PROTOCOL §11.5）；之后再次出现同一个键，就当作新的一帧。这对 255 FPS 以内的发送端都是安全的。

## 2.3 失败原因

识别失败时返回一个原因：

| reason | 含义 | 常见原因 |
|---|---|---|
| `finders` | 定位图案候选少于 3 个 | 码不在画面里、太小、太糊 |
| `geometry` | 没有像网格的三角组合 | 只拍到一部分；画面里有别的干扰图案 |
| `header` | 所有组合都读不出帧头 | 太糊、格子太小（< 3 像素） |
| `lattice` | 校准点找不到（内部使用，会继续尝试下一组角） | 假的定位图案 |

## 2.4 演示应用的调度（省电的关键）

除识别器本身外，Web 演示还用下面几种办法降低计算量和功耗（也就是手机发热）：

1. **跟随发送端帧率**：从帧序号估计发送端帧率。拿到一个新帧后，只要这一帧还在屏幕上（约 0.75 个发送周期内）就不再识别；拿到的是已解出的帧，则等约 1/3 个周期再试。识别次数因此从每个相机帧一次的约 30 次/秒，降到约 1.6 倍发送帧率。
2. **感兴趣区域（ROI）+ 自适应分辨率，在 GPU 上完成**：找到码之后，主线程用 `createImageBitmap(video, x, y, w, h, { resizeWidth, resizeHeight })` 只取码周围的区域，并由 GPU 缩放到每格约 6 个像素，Worker 只拿到这张小图。这样省掉了整帧 1080p 的拷贝和回读，每次识别的准备时间约 3 ms。码丢失时，或手机转向导致画面尺寸变化时，恢复为整幅、原分辨率。
3. **多 Worker 并行**：识别在 Web Worker 中进行（手机 2 个，电脑最多 3 个）。默认使用 Rust/WASM 引擎（比 JS 快 1.5–2 倍），加载失败时自动回到 JS；中途切换引擎不会丢失进度（已收到的数据包会转交给新引擎）。
4. **不做无用功**：相机以 30 帧/秒运行，只有发送端达到 16 帧/秒以上时才切到 60 帧（识别次数仍跟随发送端，更快的相机只增加可选的画面，不增加识别）；画面里没有码时识别降到 5 次/秒，10 秒后降到 2 次/秒；收完后关闭相机，"再收一个"时重新打开；视频上方的面板不用背景模糊（`backdrop-filter` 会让 GPU 每个相机帧都重做一次模糊）。

## 2.5 想改进识别器？

- 先跑 `npm run test:robustness` 得到基线，它给出各种失真组合下的成功率；
- `test/batch.js` 模拟"手持、没对准"的随机场景，是最接近真机的指标；
- 两个识别器要保持一致：JS 改了，Rust 也要改（`src/rust/src/scan.rs`），然后 `npm run build:wasm`；
- 识别算法不属于协议，改动它不影响兼容性。
