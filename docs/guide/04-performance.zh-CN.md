# 4 · 性能：速度从哪里来

[指南目录](README.zh-CN.md) · [English](04-performance.md)

## 4.1 一个公式

```
实际速度 = 帧率 × 每帧码字数 × 每码字载荷 T × 捕获率 × 码字成功率 ÷ (1 + 喷泉开销)
             └──── 发送端决定：理论速率 ────┘   └───── 接收端决定 ─────┘   └ ≈ 0 ┘
```

- **理论速率**：演示发送端显示的"理论速率"，假设每一帧都被完整收到。
- **捕获率**：发送端的帧中被接收端拍到并识别过的比例（演示接收端诊断行里的"捕获"）。
- **码字成功率**：拍到的帧里解出的码字比例（"成功率"）。
- **喷泉开销**：恢复 K 个源符号平均需要 K + 1.6 个符号（最大的源块为 K + 2.4 个；见规范附录 C.2），大文件可以忽略。

所有提速手段都是在提高其中某一项。

## 4.2 与动态二维码的对比

基准是常见的动态二维码做法：QR 版本 25、纠错等级 L（每帧 1 273 字节），每秒 12 帧循环播放。

| | 动态二维码 | Lumen Code（手机屏） | Lumen Code（笔记本屏） |
|---|---|---|---|
| 网格 | 117 × 117 = 13 689 | 83 × 147 = 12 201 | 143 × 254 = 36 322 |
| 每格比特 | 1 | 2（C4） | 2（C4）/ 3（C8） |
| 每帧载荷 | 1.24 KB | 2.2 KB | 6.9 KB / 10.3 KB |
| 理论速率（12 帧/秒） | 15 KB/s | 27 KB/s | 82 KB/s / 124 KB/s |
| 丢 20% 帧时的有效倍数 | ÷ 3.25（循环，46 帧的文件） | ÷ 1.26 | ÷ 1.26 |
| 一帧拍糊一半 | 整帧作废 | 另一半码字照用 | 同左 |

丢帧 20% 是很常见的情况。此时笔记本屏上的 Lumen Code（C4）比动态二维码快约 **14 倍**（82/1.26 ≈ 65 KB/s，对比 15/3.25 ≈ 4.6 KB/s），手机屏上约 **4.6 倍**。

## 4.3 七个来源

### ① 每格更多比特（× 2 或 × 3）

QR 每个模块只有黑白，1 比特。Lumen Code 用颜色：C4 每格 2 比特，C8 每格 3 比特。C8 的三个比特直接对应 R、G、B 三个通道，一个通道判断错只错 1 比特。

默认不用 C8，是因为颜色越多，相邻颜色在相机里越接近，对模糊、摩尔纹、白平衡也越敏感。在模拟的"手持、没对准"测试中，C4 的码字成功率约 86–89%，C8 约 60%。C4 × 0.88 = 1.76 比特/格，比 C8 × 0.6 = 1.8 比特/格只少一点，但稳定得多。

### ② 更多格子（形状跟随屏幕，大小跟随物理尺寸）

- **形状**：QR 是正方形，而手机屏和相机画面都是长方形，正方形在 16:9 的区域里最多只占 56% 的面积。Lumen Code 的网格可以是任意 X × Y。参考发送端直接铺满屏幕（宽高比 ≤ 2.4），手机竖屏时就是一个细长的竖向码，格子比限制在 16:9 时多约 25%。
- **大小**：QR 的模块数由版本决定，和屏幕无关。Lumen Code 按屏幕的**物理尺寸**选格子大小，每格约 0.75 mm，接近 1080p 相机在正常距离下能分辨的极限。所以笔记本屏能放 3.6 万个格子，是 QR v25 的 2.65 倍。

### ③ 结构开销低

真实尺寸的帧中，数据格子占 92.6%（手机）到 95.3%（笔记本）。扣掉 RS 校验（16%）、每个数据包 7 字节的包头包尾和填充，**文件载荷占全部格子比特的 75–77%**。

### ④ 纠错按屏幕-相机信道定制

- 每个码字独立做 RS(n ≤ 255) 纠错，纠错等级可选 10% / 16% / 22% / 30%；
- 接收端用颜色分类的置信度找出最可疑的字节，当作擦除重试，等于把"软信息"用到了 RS 译码上；
- 每个数据包有 CRC-16，所以激进的擦除重试也是安全的，错误数据进不了喷泉解码器。

### ⑤ 码字独立 + Hilbert 排布：半张帧也有用

QR 一帧要么全部解出，要么作废。Lumen Code 每帧有十几到几十个独立的码字，沿 Hilbert 曲线各占一块紧凑区域。撕裂帧（相机拍到一半旧帧、一半新帧）、一块反光、一角失焦，都只损失那块区域里的码字（见 [指南 1](01-how-it-works.zh-CN.md) 的码字分布图）。实际拍摄中，这种部分可用的帧占很大比例。

### ⑥ 喷泉码：每一帧都是新数据

循环播放时，接收端必须收齐每一个分片，漏掉一个就要多等一整轮。漏帧率为 p、一轮 N 帧时，平均需要的轮数（等于时间倍数）：

| 文件帧数 N | 丢 10% | 丢 20% | 丢 30% |
|---|---|---|---|
| 10 | 1.76 | 2.32 | 2.93 |
| 46 | 2.41 | 3.25 | 4.17 |
| 150 | 2.93 | 3.97 | 5.14 |

喷泉码只要收到足够多的不同符号，时间倍数约为 1 / (1 − p)：丢 20% 时 1.25 倍，与文件大小无关。文件越大、丢帧越多，喷泉码的优势越大，上表范围内是 1.5 到 3.6 倍。

另外，接收端可以在任何时候开始扫描，中途移开再对准也不损失已收到的数据；文件描述符每 4 帧重复一次，随时都能拿到文件名。

### ⑦ 压缩

文本、JSON、日志、源代码在发送前用 DEFLATE 压缩，通常缩小到 1/3–1/5，相当于速度乘以 3–5。演示接收端完成后显示的"平均速度"按原始文件大小计算，所以传文本时会明显高于"接收速率"。

## 4.4 计算侧：让接收端跟得上

协议决定速度上限，接收端的计算速度决定实际能收到多少。如果识别一帧要 45 ms，而相机每 33 ms 给一帧、发送端每 83 ms 换一帧，接收端就会漏帧，还会发热。参考实现做了这些：

| 手段 | 效果 |
|---|---|
| 识别跟随发送端帧率（同一帧不重复识别） | 识别次数从约 30 次/秒降到约 1.6 × 发送帧率（12 帧/秒时约 16–20 次） |
| 已解出的帧只读帧头 | 约 8 ms，而完整识别 14–45 ms |
| 同一帧第二次只解剩下的码字 | 部分解出的帧，第二次更快 |
| ROI + 自适应分辨率（缩放到每格约 6 像素） | 像素量约 1/3，识别快约 2 倍，解码率不变 |
| ROI 裁剪和缩放交给 GPU（`createImageBitmap` 的裁剪与 resize 参数） | 不再拷贝、回读整帧 1080p，每次识别的准备时间约 3 ms |
| 收完后关闭相机；画面里没有码时降低识别频率；发送端不快时相机保持 30 帧/秒 | 阅读结果、放下手机时几乎不耗电 |
| 视频上方不用背景模糊 | 省掉 GPU 每个相机帧的一次全屏模糊 |
| Rust → WebAssembly | 比 JS 快 1.5–2.1 倍（原生 Rust 1.6–2.6 倍） |
| 多个 Worker 并行 | 手机 2 个，电脑最多 3 个 |
| 发送端 GPU 合成（每格 1 像素的画布 + 静态遮罩，GPU 放大） | 发送端每帧 CPU 开销接近零 |

在 Apple M2 上完整识别一张 1080p 照片：手机尺寸的码 JS 14–16 ms、WASM 9–10 ms；笔记本尺寸的码 JS 41–45 ms、WASM 21 ms。

## 4.5 实际限制速度的是什么

按影响从大到小：

1. **格子在相机画面里的像素数**。≥ 4.5 像素很稳，3.4–4.5 勉强，< 3.4 基本读不出。它取决于屏幕上的格子大小、拍摄距离和相机分辨率。"密度"调高后每帧数据更多，但格子更小，成功率会下降。
2. **相机**：多数手机网页只能拿到 30 帧/秒；卷帘快门导致撕裂；自动曝光在亮屏前可能过曝；运动模糊。
3. **显示器**：60 Hz 屏幕上，帧率最好是 60 的约数（10、12、15、20、30），否则每帧的显示时长忽长忽短。
4. **接收端算力**：诊断行中"捕获"低于 80%、同时引擎耗时很高，就是算力不够，应换 WASM 或降低识别分辨率。

调优顺序：先保证成功率（格子像素数 ≥ 4.5、成功率 ≥ 90%），再提高帧率，最后才考虑提高密度或换 C8。有余量时，接收端会提示"识别有余量：可把发送端帧率提高到约 N"。

## 4.6 各环节的实测耗时

方法：`node test/bench.js`（JavaScript，Node 22）和在 `src/rust` 中运行 `cargo run --release --example measure -- bench`（Rust，原生）。每个值是预热一次后多次重复的平均值。机器：Apple M2 Pro，macOS 26.5。T = 200 字节；RS(255, 215) 是大网格的默认码字。

| 环节 | JavaScript | Rust |
|---|---|---|
| RS 编码，一个码字 | 12.8 µs | 8.0 µs |
| RS 译码，无错码字 | 33 µs | 33 µs |
| RS 译码，20 个错误字节 | 87 µs | 75 µs |
| 喷泉码：一个编码符号 | 1.2 µs | 0.12 µs |
| 喷泉码：从 K + 10 个符号解 K = 1000 | 8.4 ms（24 MB/s） | 0.8 ms（250 MB/s） |
| 喷泉码：从 K + 10 个符号解 K = 16 384 | 105 ms（31 MB/s） | 20 ms（164 MB/s） |
| 生成帧的格子，150 × 240 C4（34 个码字） | 0.76 ms | 0.76 ms |
| 解压（2.2 MB 文本的 zlib 流） | 147 MB/s | — |
| 接收端，从数据包完成 2 MB 的传输（10 064 个数据包） | 168 ms（12 MB/s） | 25 ms（79 MB/s） |

接收端处理数据包和解码的开销远小于识别（§4.4）：在 100 KB/s 的相机链路上，识别之后的全部处理只占一个核的约 1%。

## 4.7 还能更快吗？改进路线

改进按是否要改协议分为三类。不改协议的随时可以做，并且兼容所有现有实现。

### A. 只改接收端（不改协议）

| 改进 | 原理 | 预期收益 | 难度 |
|---|---|---|---|
| **跨帧软合并** | 同一帧通常被拍到 2–3 次，目前每次独立解码。改为把多次拍摄中同一格子的颜色似然相加后再分类，单次都解不出的码字合起来可能解得出 | 边缘条件（格子 3.4–4.5 像素）下成功率明显提高，大约相当于密度能再调高一档 | 中 |
| **去模糊 / 串扰均衡** | 模糊让每个格子混入邻居的颜色；用测得的模糊核做一次均衡（每格减去邻居的加权贡献） | 可用更小的格子，密度 +20–30% | 中 |
| **60 帧/秒拍摄** | 在支持的设备上请求 60 帧/秒，并用 `requestVideoFrameCallback` 精确取帧 | 发送端可提到 20–24 帧/秒 | 低（受设备限制） |
| **WebGPU 识别** | 采样与分类高度并行，适合 GPU | 识别耗时再降数倍，发热更低 | 高 |

### B. 只改发送端（不改协议）

| 改进 | 原理 | 预期收益 |
|---|---|---|
| 与刷新率对齐的帧率 | 120 Hz 屏幕上用 20、24、30 帧/秒，每帧显示时长恒定 | 撕裂更少，可用更高帧率 |
| 按接收端提示调参 | 没有回传通道，但人可以看接收端提示调整帧率、密度 | 已实现（提示"可把发送端帧率提高到约 N"） |

### C. 改协议（1.0 不采用，留给以后的版本）

| 改进 | 原理 | 代价 | 建议 |
|---|---|---|---|
| 帧头纠错码 | 给帧头加 BCH 或短 RS 码 | 每份副本多 21–35 格；帧格式变化 | **不采用**：实测帧头读不出时，最好的副本通常错 15–30 位（读的位置就偏了），纠错码只能救约 1/4。改为接收端"沿用上一个正确帧头"（已实现，不改协议），在同一测试中拿到了完美纠错码的全部收益（C4 码字成功率 +3.7 个百分点） |
| LDPC / 软判决码替代 RS | 直接利用每个格子的颜色置信度，编码增益约 1.5–2 dB | 解码复杂度高，实现难度大 | 留给 v2 |
| 更多颜色（C16） | 每格 4 比特 | 相机颜色分辨能力不够，成功率会大幅下降 | 不建议 |

下一步最划算的是 A 类的跨帧软合并：不用改协议，直接提高成功率。帧头格式维持现状，已在 1.0 冻结。
